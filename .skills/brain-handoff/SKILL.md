# brain-handoff

## 什么时候使用

当一个已经完成初始化的 `*-brain` 需要正式接手、形成项目理解报告或建立可供后续工作的交接基线时，使用本流程。

典型触发包括：

- 用户明确要求“接手项目”“先了解项目”“汇报当前状态”或“形成交接”；
- 新 agent 被要求在执行具体任务前，先系统复述项目目标、现实状态、漂移和未知项；
- 用户希望判断当前 brain 是否足以让其他 agent 继续工作。

以下情况不使用本 skill：

- 仓库尚未初始化、只完成部分初始化或状态信号冲突；此时读取 `.skills/brain-initializer/SKILL.md`；
- 用户直接给出普通具体任务，且没有要求正式接手或项目状态报告；此时按 `AGENTS.md` 的事实层级建立完成该任务所需的最小上下文即可；
- 同一任务中的后续对话，除非出现新的重大状态漂移或用户再次明确要求交接。

## 核心原则

- **正式接手与普通任务分流。** 正式接手生成结构化理解；普通任务不为例行理解汇报增加等待。
- **读取有界。** 先读权威入口和当前状态，只按 CURRENT 指向、任务命中或确有追溯需要读取少量事件、Draft 或 Archive，不全文扫描历史。
- **事实分层。** `Releases/` 表达“应该是什么”，`.records/CURRENT.md` 表达“现在怎样”，事件记录表达“发生过什么”；外部代码、服务和运行状态需要另行实时验证。
- **默认只读。** 接手本身不创建 Draft、Record、Release，不更新 CURRENT，也不触发 Git、Star 或其他外部写操作。
- **只为实质歧义询问。** 用户已经授权的具体任务不重复确认；只有歧义会实质改变结果、需要扩权或无法安全继续时才暂停。

## 执行流程

### 1. 确认仓库状态

- 查看当前分支和工作区，识别用户或其他 agent 的并行修改；只读检查不得整理或提交这些改动。
- 按 `AGENTS.md` 的状态路由确认这是已初始化 brain。若属于未初始化、部分初始化或无法可靠判断，停止本流程并转入 initializer。
- 检查 `.brain-template.json` 是否有效以及协议基础设施是否有明显缺口；发现问题时只纳入接手报告，不自动升级。

### 2. 建立规范性理解

- 先列出 `Releases/`，选择项目总览、当前规范和与用户任务直接相关的核心入口；不要为了“完整”而逐篇通读全部 Release。
- 提炼项目定位、目标与非目标、主要读者、关键术语、不可违反的项目专属约束，以及当前可照着执行的规则。
- Release 之间存在替代关系时，以明确标注的当前版本为准；无法判断时保留为未知项。

### 3. 建立现实状态理解

- 完整读取 `.records/CURRENT.md`，提炼当前阶段、正在进行、最近关键变化、文档与现实漂移、下一步和仍相关的记录。
- 只读取 CURRENT 明确指向、当前任务命中或用于解释重大漂移的少量 `.records/events/`。
- 任务依赖外部代码仓库、线上服务、数据或第三方状态时，区分历史记录与实时证据；在用户授权范围内进行必要的只读验证，无法验证时明确标注。

### 4. 按需补充背景

- 仅在 Release 与 CURRENT 不足以解释项目意图、方案演进或当前任务时读取相关 Draft。
- Draft 只能作为未定稿参考，不得把其中结论写成当前规范。
- 仅在追溯替代关系、放弃原因或历史依据确有必要时读取 Archive；不得据此执行当前工作。

### 5. 识别漂移、风险与未知项

- 对照规范、CURRENT、必要事件和实时证据，列出会影响后续工作的冲突或漂移。
- 区分已验证、文档已确认、用户或第三方报告、合理推定和未知，不能用笼统的“已了解”掩盖证据差异。
- 只保留会影响决策、执行范围或验收的未知项；不把所有缺少的信息都升级为阻塞。

### 6. 报告并决定是否继续

接手报告按需包含：

- 项目是什么，以及当前目标与非目标；
- 当前实际阶段和正在进行的工作；
- 关键约束与不可越过的边界；
- 规范与现实的漂移、风险和证据不足；
- 建议的下一步，以及哪些事项仍需用户决定。

报告之后按以下语义处理：

1. **用户只要求接手或状态报告，没有给出具体任务**：报告完成即交付，不要求用户回复“确认”；等待用户提出下一项任务。
2. **用户同时给出了明确、已授权的具体任务**：把接手理解作为简短的非阻塞进度说明；没有会实质改变执行结果的歧义时，直接继续完成任务，不等待“确认”“理解正确”或同义回复。
3. **发现实质歧义或缺少必要授权**：只说明具体冲突、它会如何改变结果，以及需要用户决定的最小问题；不要把完整接手报告包装成笼统的最终确认。
4. **用户已经确认过同一范围**：不得因重新读取、列出计划或补充细节再次询问；只有范围扩大、破坏性变化、外部写操作或其他新增授权需求才另行询问。

## 与其他 skill 的关系

- 接手过程中发现未初始化或部分初始化信号：转入 `brain-initializer`，遵守其项目定义确认门槛。
- 后续具体任务需要写 Draft、创建检查点、更新 Release 或升级协议：到达对应触发条件时再读取相应 skill；接手本身不提前加载或执行它们。
- 接手报告只是当前理解，不替代 Release、CURRENT、事件记录或外部实时验收。

## 验收标准

- 已覆盖项目身份、当前状态、关键约束、漂移与未知项，且每类结论的证据层级清楚。
- 没有为建立上下文全文扫描历史，也没有把 Draft 或 Archive 当成权威事实。
- 没有因为接手本身修改仓库、创建 Record、执行 Git、升级模板或询问 Star。
- 用户已经给出具体任务时，没有把接手汇报变成重复确认门槛；存在真正阻塞时，问题具体且只请求最小必要决策。

## 禁止事项

- 不把“新 agent”机械等同于必须停下来等待用户确认。
- 不在没有实质歧义时要求用户确认项目复述、执行计划或已经授权的任务。
- 不为显得完整而扫描全部 Release、Record、Draft、Archive 或 Git 历史。
- 不把历史文档、旧 Record 或推定当成当前外部系统的实时证据。
- 不以接手为由执行任何写入、Git 交付、模板升级、Star 或其他外部操作。
